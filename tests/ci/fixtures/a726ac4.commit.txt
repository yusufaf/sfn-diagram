feat(png): add loadSystemFonts and skip the system font scan by default (#362)

* perf(png): load one font file instead of scanning every system font

resolvePngFontOptions returned loadSystemFonts: true from all three
branches, so resvg re-parsed every installed font on every Resvg
construction - even when the caller had named an exact file. The probe
branch already knew the file: FONT_PROBES entries are { family, path },
and the code resolved match.path, threw it away, and handed resvg the
whole of FONT_DIRS[platform] instead.

loadSystemFonts now resolves separately from the font source: the new
loadSystemFonts option, then SFN_DIAGRAM_PNG_LOAD_SYSTEM_FONTS, then
false if a concrete font file or directory resolved and true if nothing
did. The probe branch hands resvg fontFiles: [match.path] alone.

exportPng on examples/order-processing.asl.json, Windows 11, warm cache,
four runs: 248ms -> 18ms, output byte-identical at 19162 bytes. Isolated
through @resvg/resvg-js on a 200x100 one-text SVG, three runs each:
system scan + dirs 267/226/219ms, dirs only 88/99/93ms, one fontFiles
entry 1/1/1ms - identical bytes and identical painted-pixel counts in
all three.

The tradeoff: glyphs the resolved font does not cover no longer fall
back. The same CJK probe drops from 562 painted pixels to 136 (tofu
boxes, not blank). Set loadSystemFonts: true, or the env var, to get the
previous behaviour back - the forced-on path returns the exact option
shape the probe branch used to return unconditionally.

A family name alone cannot be located without a search path, so
fontFamily-only callers, and SFN_DIAGRAM_PNG_FONT_FAMILY on its own,
keep the scan: probed with loadSystemFonts: false it renders 0 pixels.
Explicit fontDirs that are all pruned as non-existent keep it too.

Tests assert painted pixels rather than a valid PNG, since a font that
fails to resolve still produces a perfectly valid blank one. tests/
decodePng.ts inflates and unfilters the engine's own output; a fully
covered image decoding to exactly 200*100 opaque pixels is what keeps a
zero count meaningful. Verified the glyph assertion fails (0 pixels)
when the font is made unresolvable.

* fix(png): only skip the font scan when a readable font file is known

Review on #362 found three ways the first cut could render a silently
blank PNG, and one undocumented loss. Verified each against the real
engine before changing anything, by painted-pixel count.

An existing directory or a bare family name does not prove a loadable
font. `fontDirs: [<existing empty dir>]` with the scan off paints 0
pixels against 581 with it on, so an `-e SFN_DIAGRAM_PNG_FONT_DIRS=/fonts`
mount holding nothing fontdb can parse would have lost every label.
`fontDirs` and `SFN_DIAGRAM_PNG_FONT_DIRS` now keep the scan on.

`fontFiles` entries are not checked for existence, so a typo path also
turned the scan off: `fontFiles: ['C:/nope/missing.ttf']` paints 0 pixels
and resvg does not throw, which makes the retained comment claiming it
surfaces as resvg's own error wrong. The paths still pass through
verbatim; `fileExists` now only decides whether they count as resolved.

So the rule is narrower: skip the scan only when an existing font file is
known - an entry of `fontFiles`, or a probe-table hit.

The nine env-var parsing cases were vacuous. `fileExists: () => !expected`
made the probe branch's own default equal the expectation every time, so
stubbing the reader to return undefined left all nine green -
`TRUE_VALUES`, `FALSE_VALUES`, `trim()` and `toLowerCase()` were all
untested. Inverted the stub the other way; all nine now fail under that
mutation and pass against the real source. The new fontFiles-existence
test is mutation-checked the same way.

Also documented what the single resolved face gives up besides glyph
coverage: a `font-weight="bold"` run renders at regular weight rather
than being synthesized (1240 bytes for both weights with one `fontFiles`
entry, 1240 vs 1214 with `fontDirs`). Nothing this package generates asks
for bold, but a hand-rolled SVG passed to `PngExporter` can.

The default path is untouched: exportPng on order-processing is 16ms
against 250ms forced on, still byte-identical at 19162 bytes.

* fix(png): honour a custom theme font family, and refuse an unloadable font setup

Second review pass on #362, five findings, all reproduced against the real
engine before changing anything.
